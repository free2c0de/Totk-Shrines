# Totk-Shrines

Single-file HTML app (`index.html`) hosted on GitHub Pages at https://free2c0de.github.io/Totk-Shrines/. A checklist/tracker for the 152 shrines in Zelda: Tears of the Kingdom, with search, sort, region filter, column visibility, and a "save progress to file" export that bakes checkmarks into a standalone downloaded copy of the page. No build step — it's plain HTML/CSS/JS, edited directly.

**Status as of the last session: feature-complete and working as intended, start to finish.** Current version: **v33** (see rule below). Everything below is architecture/gotcha context for picking the project back up, not a list of open work.

## Version tag

`index.html` has a `.version-tag` element (rendered as `MM.DD.YYYY vN`, no "Version:" prefix).

**Bump the version number on every single change to `index.html`, no exceptions** — including CSS-only tweaks that seem trivial. GitHub Pages sits behind a CDN with its own cache window on top of normal browser caching, and a fix can appear to do nothing simply because the live page is still serving an older build. A version bump lets you (or the user) confirm via `document.querySelector('.version-tag').textContent` whether the page actually being tested is the one that was just edited, before spending time debugging a "fix" that never deployed.

## Architecture notes (read before restructuring anything)

- **The table header is a separate `<table class="header-table">` from the body (`<table class="body-table">` inside `.table-scroll`), NOT a single table with a sticky `<thead>`.** This was a deliberate fix for a real, stubborn bug: a `position: sticky` `<thead>` inside a scrolling `<table>` bled/showed scrolled row content through the header during active scroll motion, on both real Safari/iOS and Chrome's device emulation. Every standard CSS fix was tried first (`top: -1px`, `transform: translateZ(0)`, removing `border-radius` from the scroll container, multi-layer `box-shadow` masks, switching `border-collapse` to `separate`) — none of them worked. Splitting into two tables sidesteps the whole bug class since the header is no longer sticky at all; it just sits above the scrolling area in normal flow. **Do not "simplify" this back to one table with a sticky thead** without expecting the bleed to return.
- Both tables use `table-layout: fixed` with **explicit per-column pixel widths** (`COLUMN_MIN_WIDTH`/`COLUMN_ORDER` in the script), applied to both tables identically via `data-col` attributes, which is what keeps their columns pixel-aligned despite being two separate tables. `.table-header-scroll` mirrors `.table-scroll`'s horizontal `scrollLeft` via a `scroll` listener so the header stays in sync when there's enough columns to need horizontal scrolling. Each visible column keeps its own real minimum width — never squeeze columns to force-fit the viewport, or content (region pills, "Skyview Tower" header text, etc.) will overlap/clip; let the table overflow and scroll horizontally instead.
- **Column visibility** (`COLUMNS`, `COLUMN_ORDER`, `AUTO_COL_BREAKPOINTS`, `computeAutoHiddenCols()`, `applyColumnVisibility()`): Shrine, Found, Region, and Tower are shown by default at any width; only the `#` column auto-hides below 640px. Manually toggling anything in the Columns dialog (toolbar button) switches to permanent manual mode via `userHasSetColumns()`/`markUserSetColumns()`, which then ignores the width-based defaults entirely. **Column choices persist in `localStorage`** (`totk-shrine-hidden-cols`, `totk-shrine-cols-user-set`) — this was briefly disabled mid-project for easier testing, then re-enabled; if a future session finds it disabled again, that's a regression, not intentional.
- **Coordinate tooltips** on Shrine/Skyview Tower cells: hover shows them on desktop. On touch, a long-press (500ms) activates **"coords mode"** (`coordsModeActive`), which then shows the tooltip on a plain tap on *any* Shrine or Tower cell (not just the one long-pressed) and persists across columns until the user taps anything outside those two columns. While coords mode is active, tapping a Shrine cell shows its coordinates *instead of* toggling "found" — this was a deliberate fix; without it, browsing coordinates by tapping around would accidentally mark shrines found. `suppressNextClick` prevents the click that ends a long-press from also toggling "found"; it's cleared both by the next document click and by a timeout on `touchend` (some mobile browsers don't fire a synthetic `click` after a long press, which would otherwise leave taps permanently suppressed). `isRecentTouch()`/`lastTouchTime` guards the desktop hover handlers (`mouseenter`/`mousemove`/`mouseleave`) from firing on the synthetic mouse events some mobile browsers dispatch after a real tap — without that guard, every tap on Shrine/Tower briefly showed the tooltip even without a long press.
- **Shrine name cells are also click-to-toggle-found**, independent of the checkbox, because on narrow phones the Found column can end up scrolled out of view while Shrine stays visible. This is suppressed while coords mode is active (see above) and while the lock is engaged (see below).
- **Lock toggle** (glowing lock icon at the right edge of the "Shrine" column header, `#lockToggle`/`lockActive`, persisted in `localStorage` under `totk-shrine-lock`): when locked, clicking a shrine that's already found (via either the checkbox or the shrine name) is a no-op — it will not deselect. Checking a *new*, not-yet-found shrine still works normally while locked; only deselecting is blocked. This exists because it's easy to accidentally tap a found shrine and lose that checkmark.
- **The Found checkbox** is a fully custom-styled circle (`appearance: none`), not a native checkbox. The teal-to-amber gradient background is always visible (unchecked or checked); when checked, it additionally gets a glow ring (`box-shadow`) and overlays the actual shrine icon image (see Assets below) via a `::after` pseudo-element background-image, masked into a soft circular fade with `mask-image: radial-gradient(circle closest-side, ...)` — the same masking trick used everywhere else the icon appears, needed because the source PNG's near-transparent edges still show as a faint square at small sizes without it.
- **`box-shadow`/`color-mix()` combined with `var()` on an `appearance: none` checkbox silently resolves to zero alpha in this environment** (confirmed via direct testing — works fine on plain `<div>`s, breaks specifically on the styled checkbox). Worked around with plain pre-computed `rgba()` custom properties (`--accent-ring`, `--accent-glow`) instead of `color-mix()` for anything touching the checkbox's glow. Keep using those variables rather than reintroducing `color-mix()` there.

## Assets

- `Assets/Totk Shrine Icon.png` — the **actual in-game shrine icon**, supplied by the user (not AI-generated; Nintendo's icon is copyrighted/trademarked, so it was intentionally sourced by the user rather than traced/recreated). Used for the favicon, the header icon next to "Shrines of Hyrule", the marker before every shrine name, and the checked-checkbox overlay. Referenced with the space URL-encoded as `Assets/Totk%20Shrine%20Icon.png`. If this file is ever missing after a fresh clone, all four of those usages will silently 404 — remind the user it must be committed and pushed alongside `index.html` (it's easy to forget since GitHub Desktop treats it as a separate new file).
- Do not attempt to recreate this icon as an SVG from scratch — that was tried once (an original, non-infringing geometric design) and the user preferred switching to the real asset instead once they supplied it.
- The PNG's edges have alpha that fades close to (but not exactly) zero, which shows as a faint square at small render sizes. The fix used everywhere: `mask-image: radial-gradient(circle closest-side, black 55%, transparent 100%)` (with a `-webkit-mask-image` fallback) forces a clean circular fade regardless of the source file's own edges. Apply this same mask to any new usage of the icon rather than relying on the PNG's own transparency.

## Local testing workaround

Claude's own Browser-pane preview cannot execute JavaScript against `file://` URLs (renders as an inert static snapshot), and this sandbox has neither Python nor Node available. The workaround used throughout this project: launch a minimal PowerShell `System.Net.HttpListener` static file server as a **fully detached process** (via `Start-Process powershell.exe -ArgumentList "-NoProfile","-WindowStyle","Hidden","-File",$scriptPath` pointing at a small `.ps1` script containing the listener loop — NOT `Start-Job`, which dies when the calling shell session ends), then point the Browser pane at `http://localhost:8901/index.html`. This gave real JS execution, `resize_window` viewport testing, and `getComputedStyle` inspection without needing a real device for every check. The server needs restarting (same pattern) after a PC reboot or if `localhost:8901` stops responding.

A heavily-reused test tab (many reloads/clicks across a long session) occasionally produced stale/incorrect `getComputedStyle` readings (e.g. a real `box-shadow` reporting zero alpha) that a genuinely fresh tab/navigation did not reproduce — if a computed-style check looks wrong but the underlying CSS rule text is clearly correct, try a fresh `preview_start` navigation before concluding there's a real bug.

The "Claude for Chrome" extension was also tried for live device-emulation debugging, but hit a hard wall: Chrome only allows one debugger attached to a tab at a time, so having DevTools' device toolbar open on a tab conflicted with the extension's own automation on that same tab, and returned an opaque "Cannot access a chrome-extension:// URL of different extension" error triggered by that conflict specifically. That path was abandoned in favor of the local-server approach above plus the user's own real-device testing.

## Testing loop

The user tests primarily on a real Android phone (Chrome) and a real iPhone, plus occasionally Chrome DevTools' device emulation on PC, and commits/pushes changes via GitHub Desktop. There is no CI — every fix needs a real round-trip (push → wait for GitHub Pages/Fastly cache → reload on device) to confirm, which is the whole reason the version-tag rule above exists.
